Azure Network Segmentation Using Network Security Groups (NSGs) and Application Security Groups (ASGs)

Project Overview

This project demonstrates how Microsoft Azure Network Security Groups (NSGs) and Application Security Groups (ASGs) can be combined to implement secure network segmentation for enterprise cloud environments. By separating workloads into logical security groups and enforcing role-based traffic policies, the solution limits unnecessary communication, reduces the attack surface, and supports Zero Trust networking principles.

Business Scenario

A fictional organization hosts both public-facing web servers and internal management servers within Azure. Because each workload performs different business functions, they require different network security policies. Web servers should only receive HTTP traffic from users, while management servers should only accept Remote Desktop (RDP) connections from authorized administrators. The objective is to implement secure network segmentation that prevents unauthorized access while maintaining operational efficiency.

Security Objectives

  • Deploy Azure Virtual Network infrastructure.
  • Create Application Security Groups for workload segmentation.
  • Deploy separate Web and Management virtual machines.
  • Configure Network Security Groups with role-based security rules.
  • Restrict traffic using Application Security Groups.
  • Validate network segmentation using Azure Network Watcher.
  • Demonstrate defense-in-depth using Azure native networking services.

The architecture separates Azure virtual machines into logical security groups using Application Security Groups while Network Security Groups enforce different inbound access policies for web and management workloads. This approach simplifies rule management while strengthening network security and limiting lateral movement between workloads.

Implementation Overview

The following implementation phases demonstrate the complete deployment of a segmented Azure network using Virtual Networks, Application Security Groups, Network Security Groups, Virtual Machines, and Azure Network Watcher. Each phase includes configuration details, screenshots, validation results, and the security benefits gained from the implementation.

Implementation Phase 1 – Create the Resource Group and Azure Virtual Network

Objective

The first phase established the foundational Azure infrastructure required for network segmentation. A dedicated Resource Group and Azure Virtual Network (VNet) were created to provide a secure, isolated environment where networking resources could be centrally managed. This infrastructure serves as the basis for deploying virtual machines, configuring Application Security Groups (ASGs), and enforcing Network Security Group (NSG) policies throughout the project.

Implementation

A new Resource Group named RG-SecurityLab was created within the selected Azure region to logically organize all project resources. Following this, an Azure Virtual Network named VNet-SecurityLab was deployed with dedicated subnets to host the Web Server and Management Server workloads. This logical separation forms the foundation of secure network segmentation.

Why This Phase Matters

Every secure Azure deployment begins with a properly designed networking foundation. By organizing resources into a dedicated Resource Group and isolating workloads inside an Azure Virtual Network, administrators gain centralized management, improved visibility, and a controlled environment where security policies can be consistently enforced.

Implementation Phase 2 – Create Application Security Groups (ASGs)

Objective

With the Azure networking infrastructure in place, the next phase focused on creating Application Security Groups (ASGs). Unlike traditional IP-based security rules, ASGs allow Azure administrators to logically group virtual machines according to their business function. This simplifies Network Security Group (NSG) management while improving scalability, readability, and maintainability of security policies.

Implementation

Two Application Security Groups were created to represent the different workloads within the environment. The first ASG, ASG-Web, was designated for public-facing web servers, while the second, ASG-Management, was created for administrative management servers. These logical groups would later be referenced by Network Security Group rules instead of individual IP addresses.

Figure 4. Creation of the Application Security Group used to logically group Azure Web Server virtual machines.

Figure 5. Application Security Group created for Management Server workloads requiring administrative access.

Application Security Groups Created

Application Security Group Purpose
ASG-Web Groups public-facing web servers for HTTP traffic policies.
ASG-Management Groups management servers requiring secure administrative access.

Why This Phase Matters

Managing firewall rules based on IP addresses quickly becomes difficult in large cloud environments where virtual machines are frequently added, removed, or reconfigured. Application Security Groups solve this problem by allowing security policies to target workload roles instead of individual machines, making network segmentation more flexible and significantly easier to manage.

Security Benefits

  • Groups virtual machines according to business function.
  • Eliminates dependence on static IP addresses within security rules.
  • Simplifies Network Security Group management.
  • Supports scalable enterprise cloud environments.
  • Improves consistency of role-based security policies.
  • Strengthens Zero Trust network segmentation.

Outcome

The Application Security Groups were successfully created to represent Web Server and Management Server workloads. These logical groups provide the foundation for applying role-based Network Security Group rules during the next implementation phases, enabling secure and scalable network segmentation.

Implementation Phase 3 – Deploy Web and Management Virtual Machines

Objective

After creating the Application Security Groups, the next phase involved deploying the workloads that would operate within the segmented Azure network. Two virtual machines were provisioned to simulate a real-world enterprise environment: a Web Server responsible for hosting public-facing services and a Management Server dedicated to administrative operations. Separating these roles enables independent security policies to be applied according to business requirements.

Implementation

A Web Server virtual machine was deployed with Internet Information Services (IIS) installed to provide HTTP services. A separate Management Server virtual machine was also deployed to support administrative tasks through Remote Desktop Protocol (RDP). Although both virtual machines reside within the same Azure Virtual Network, they perform different functions and will later receive different network security policies through Application Security Groups and Network Security Groups.

Implementation Phase 4 – Associate Virtual Machine Network Interfaces with Application Security Groups

Objective

After deploying the Web Server and Management Server virtual machines, the next phase involved associating each virtual machine's Network Interface Card (NIC) with its corresponding Application Security Group (ASG). This enables Azure Network Security Groups to apply security policies based on application roles rather than individual IP addresses, creating a more scalable and manageable security architecture.

Implementation

The Network Interface Card (NIC) for the Web Server virtual machine was associated with ASG-Web, while the NIC for the Management Server virtual machine was associated with ASG-Management. Once these associations were completed, Network Security Group rules could reference the Application Security Groups directly, eliminating the need to configure firewall rules using individual virtual machine IP addresses.

Figure 8. Virtual machine Network Interface Cards associated with their respective Application Security Groups to enable role-based security policy enforcement.

Application Security Group Associations

Virtual Machine Application Security Group Business Function
Web Server VM ASG-Web Hosts public-facing web services.
Management Server VM ASG-Management Provides secure administrative access.

Why This Phase Matters

Application Security Groups separate security policy management from network addressing. Rather than creating firewall rules for individual virtual machines, administrators define rules for application roles. As workloads are added, removed, or replaced, security policies remain consistent without requiring updates to IP-based firewall rules. This significantly improves the scalability and maintainability of enterprise Azure environments.

Security Benefits

  • Implements role-based network security.
  • Eliminates dependence on static IP addresses.
  • Simplifies Network Security Group rule management.
  • Supports dynamic cloud environments where workloads frequently change.
  • Reduces administrative overhead for firewall policy management.
  • Strengthens Zero Trust architecture through workload identity.

Outcome

Both virtual machines were successfully associated with their respective Application Security Groups. The environment is now prepared for the next phase, where Network Security Groups will enforce different traffic rules for Web Server and Management Server workloads based on their ASG membership.

Implementation Phase 5 – Configure Network Security Groups (NSGs)

Objective

With the Azure infrastructure fully deployed and virtual machines assigned to their respective Application Security Groups, the next phase focused on configuring Network Security Groups (NSGs). NSGs provide stateful packet filtering for Azure resources and enforce inbound and outbound traffic rules. By combining NSGs with ASGs, security policies can be applied based on application roles rather than IP addresses, supporting scalable enterprise network segmentation.

Implementation

Separate Network Security Group rules were configured for the Web Server and Management Server workloads. The Web Server was permitted to receive HTTP traffic on TCP port 80, allowing users to access hosted web applications. The Management Server was configured to allow Remote Desktop Protocol (RDP) traffic on TCP port 3389 for authorized administrators. All other unnecessary inbound traffic remained blocked by default, following the principle of least privilege.

Figure 9. Network Security Group configured to allow HTTP traffic for Web Server resources associated with the ASG-Web Application Security Group.

Figure 10. Network Security Group configured to allow secure Remote Desktop (RDP) connections for Management Server resources associated with the ASG-Management Application Security Group.

Application Security Group Allowed Protocol Purpose

All Other Traffic Denied Reduces unnecessary network exposure.

Why This Phase Matters

Network Security Groups act as the primary network firewall within Azure. Instead of permitting unrestricted communication between workloads, NSGs enforce role-specific traffic policies that align with business requirements. Combining NSGs with Application Security Groups simplifies administration, improves scalability, and significantly reduces the risk of unauthorized network access and lateral movement.

Security Benefits

  • Implements least-privilege network access.
  • Allows only required application traffic.
  • Blocks unauthorized inbound connections.
  • Reduces the risk of lateral movement.
  • Uses Application Security Groups for scalable rule management.
  • Strengthens Zero Trust network architecture.
  • Provides centralized and consistent network policy enforcement.

Outcome

Network Security Groups were successfully configured to enforce role-based traffic policies for both Web Server and Management Server workloads. Only authorized HTTP and RDP traffic was permitted, while all unnecessary inbound traffic remained blocked. The segmented Azure environment was now ready for security validation and connectivity testing.

Objective

Implementation

The Web Server was accessed through a web browser to verify HTTP connectivity, while the Management Server was accessed using Remote Desktop Protocol (RDP). These tests confirmed that only the services explicitly permitted by the Network Security Groups were available.

Implementation Phase 7 – Validate Network Security Using Azure Network Watcher

Objective

The final implementation phase focused on validating the effectiveness of the network segmentation architecture using Azure Network Watcher. Rather than assuming that the configured Network Security Groups (NSGs) were functioning correctly, Azure Network Watcher was used to verify connectivity, inspect security rule evaluation, and confirm that network traffic followed the intended security policies. This validation provides assurance that the implemented controls are operating as designed.

Implementation

Azure Network Watcher was used to analyze connectivity between Azure resources and evaluate how Network Security Group rules affected traffic flows. The validation confirmed that HTTP traffic was permitted to the Web Server, Remote Desktop (RDP) traffic was allowed only to the Management Server, and all other unauthorized traffic remained blocked according to the configured security policies.

Lessons Learned

This project demonstrated that effective network security extends beyond simply deploying firewall rules. Proper network segmentation requires logical workload grouping, carefully designed security policies, and continuous validation to ensure that only authorized communication is permitted between resources.

Application Security Groups significantly simplify Network Security Group management by allowing administrators to define security policies according to business roles rather than individual IP addresses. This approach improves scalability, reduces administrative complexity, and supports dynamic cloud environments where workloads frequently change.

The project also reinforced the importance of validating implemented security controls. Using Azure Network Watcher confirmed that network segmentation was operating correctly and that unauthorized traffic remained blocked. Together, Azure Virtual Networks, Application Security Groups, Network Security Groups, and Azure Network Watcher provide a layered defense-in-depth architecture that aligns with Zero Trust networking principles.
