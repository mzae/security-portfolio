Azure Firewall Configuration & Testing

A hands-on cloud security project demonstrating the deployment, configuration, and validation of Microsoft Azure Firewall to protect Azure workloads using centralized traffic inspection, network security policies, and controlled routing.

Executive Summary

Azure Firewall is Microsoft's cloud-native, fully managed, stateful firewall service that provides centralized protection for Azure resources. It enables organizations to inspect, filter, and monitor both inbound and outbound network traffic while enforcing consistent security policies across cloud environments.

In this project I deployed Azure Firewall, configured routing, implemented application and network rules, enabled DNS Proxy, and validated firewall functionality through connectivity testing. The project demonstrates practical cloud security skills and follows Microsoft Azure security best practices.

Business Scenario

Organizations increasingly host business-critical workloads in Microsoft Azure. Without centralized network security, virtual machines and applications may communicate directly with the Internet, increasing the attack surface and reducing visibility into network activity.

To strengthen cloud security, Azure Firewall was deployed as the primary network security control. The firewall provides centralized traffic inspection, policy enforcement, and monitoring, helping ensure that only authorized traffic reaches protected Azure resources.

Step 2 – Deploy Azure Firewall

Objective

After the Azure networking environment was successfully provisioned, Azure Firewall was deployed to provide centralized network security. Azure Firewall is a cloud-native, fully managed, stateful firewall service that protects Azure resources by inspecting, filtering, and controlling network traffic based on administrator-defined security policies.

Deployment Process

The firewall was deployed through the Azure Portal and associated with the previously created AzureFirewallSubnet. During deployment, a dedicated public IP address was allocated to the firewall, allowing it to securely inspect and manage inbound and outbound traffic. Once provisioning completed successfully, Azure Firewall became the central security gateway for the virtual network.

Figure 3. Azure Firewall successfully deployed and associated with the Azure Virtual Network.

Outcome

Step 3 – Configure User Defined Routes (UDRs)

Objective

After deploying Azure Firewall, the next step was to configure User Defined Routes (UDRs). By default, Azure routes traffic directly between resources and the Internet. To ensure that every outbound connection is inspected by Azure Firewall, custom route tables were created and associated with the workload subnet.

Configuration Process

A Route Table was created within the Azure Resource Group and configured with a custom route that directed outbound traffic to the Azure Firewall private IP address. The Route Table was then associated with the workload subnet, ensuring that all virtual machines in the subnet used the firewall as their next hop for Internet-bound traffic.

Figure 4. Creating a User Defined Route (UDR) to redirect outbound traffic through Azure Firewall.

Route Table Association

Once the custom route was created, the Route Table was associated with the workload subnet. This ensured that every virtual machine within the subnet automatically forwarded outbound traffic through Azure Firewall before accessing external resources.

Security Benefits

  • Forces all outbound traffic through Azure Firewall.

Why This Step Matters

Azure Firewall can only inspect traffic that reaches it. Without User Defined Routes, workloads could communicate directly with the Internet, bypassing firewall policies entirely. Configuring UDRs ensures that all outbound traffic follows a controlled path through Azure Firewall, allowing administrators to enforce security policies, monitor activity, and reduce the organization's attack surface.

Outcome

The User Defined Routes were successfully configured and associated with the workload subnet. All outbound traffic was now routed through Azure Firewall, preparing the environment for the creation of Application Rules that would control access to specific web services and domains.

Step 4 – Configure Application Rules

Objective

With Azure Firewall successfully deployed and all outbound traffic redirected through it, the next step was to configure Application Rules. These rules operate at Layer 7 (Application Layer) and allow administrators to control outbound web traffic based on Fully Qualified Domain Names (FQDNs) instead of IP addresses.

Configuration Process

An Application Rule Collection was created within Azure Firewall Policy. Specific domains required by the lab environment were added as allowed destinations while all other web traffic continued to be evaluated against the configured firewall policy. This approach demonstrates how Azure Firewall can enforce web access restrictions using domain names rather than relying solely on IP-based filtering.

Figure 6. Configuring Azure Firewall Application Rules to allow traffic only to approved web destinations.

Logging & Monitoring Azure Firewall Diagnostic Logs provide visibility for auditing and investigations. ✔ Implemented

Why Application Rules?

Traditional firewalls often rely on IP addresses to filter traffic. However, cloud services frequently change IP addresses, making IP-based filtering difficult to maintain. Azure Firewall Application Rules solve this problem by filtering traffic based on domain names, allowing organizations to securely permit access to trusted services such as Microsoft, GitHub, or other approved business applications.

Security Benefits

  • Layer 7 filtering using Fully Qualified Domain Names (FQDNs).
  • Improves control over outbound web traffic.
  • Supports least privilege Internet access.
  • Reduces exposure to unauthorized websites.
  • Simplifies firewall policy management for cloud services.
  • Provides centralized governance of Internet connectivity.

Real-World Business Value

In enterprise environments, Application Rules help security teams restrict employee and server access to only approved cloud services. Rather than allowing unrestricted Internet connectivity, organizations can define a list of trusted domains that align with business requirements, reducing the risk of malware downloads, data exfiltration, and communication with malicious websites.

Outcome

Application Rules were successfully configured, enabling Azure Firewall to inspect and control outbound web traffic based on approved domain names. This strengthened the organization's network security posture and prepared the environment for the implementation of Layer 3 and Layer 4 Network Rules in the next phase of the project.

Step 5 – Configure Network Rules

Objective

After configuring Application Rules for Layer 7 traffic, the next stage involved creating Network Rules. Network Rules operate at Layers 3 and 4 of the OSI model and allow Azure Firewall to filter traffic based on source IP addresses, destination IP addresses, protocols, and port numbers. These rules provide fine-grained control over network communications between Azure resources and external networks.

Configuration Process

A Network Rule Collection was created within Azure Firewall to define which network connections were permitted. Rules were configured to allow only specific protocols and destination ports required for business operations while denying unnecessary or unauthorized traffic. This approach follows the principle of least privilege by allowing only the minimum network access required.

Figure 7. Configuring Azure Firewall Network Rules to control traffic based on IP addresses, protocols, and ports.

Why Network Rules Matter

While Application Rules secure web traffic using domain names, many enterprise services communicate directly using IP addresses and specific network ports. Network Rules provide the ability to inspect and control these communications, ensuring that only authorized connections are established between systems.

Security Benefits

  • Filters traffic at Layers 3 and 4 of the OSI model.
  • Controls communication using IP addresses and port numbers.
  • Supports the Principle of Least Privilege.
  • Blocks unauthorized network connections.
  • Reduces the attack surface of Azure workloads.
  • Provides centralized enforcement of network access policies.

Real-World Business Value

Organizations frequently use Network Rules to restrict communication between production, development, and management environments. By allowing only approved network paths and service ports, security teams reduce the risk of lateral movement, unauthorized access, and exposure of sensitive systems to unnecessary network traffic.

Outcome

Azure Firewall Network Rules were successfully configured to control network communications based on IP addresses, protocols, and ports. Together with the previously configured Application Rules, the firewall now enforced both Layer 7 and Layer 3/4 security controls. The environment was ready for DNS Proxy configuration and final validation testing.

Step 6 – Configure DNS Proxy

Objective

The final configuration task was to enable DNS Proxy within Azure Firewall. DNS Proxy allows Azure Firewall to receive and forward Domain Name System (DNS) requests on behalf of client workloads. This ensures consistent name resolution while allowing Application Rules based on Fully Qualified Domain Names (FQDNs) to function correctly.

Configuration Process

DNS Proxy was enabled within the Azure Firewall settings, allowing the firewall to process DNS queries before forwarding them to the configured DNS server. Client virtual machines were then configured to use the firewall's private IP address as their DNS server, ensuring all DNS requests passed through Azure Firewall.

Figure 8. Enabling DNS Proxy and configuring Azure Firewall to centrally manage DNS resolution.

Why DNS Proxy Matters

Azure Firewall Application Rules depend on accurate domain name resolution. Without DNS Proxy, client systems may resolve domain names independently, reducing the effectiveness of firewall policies. By centralizing DNS resolution, organizations improve policy consistency, simplify troubleshooting, and gain greater visibility into DNS-related network activity.

Security Benefits

  • Centralizes DNS resolution for Azure workloads.
  • Supports reliable enforcement of FQDN-based Application Rules.
  • Improves visibility into DNS requests.
  • Simplifies DNS policy management across cloud environments.
  • Helps detect suspicious or unauthorized DNS activity.
  • Strengthens overall network governance.
  • Centralized DNS requests improve monitoring and troubleshooting.

Real-World Business Value

In enterprise cloud environments, centralized DNS resolution helps security teams maintain consistent security policies across hundreds or thousands of workloads. It also improves incident investigations by providing a single point for monitoring DNS activity and identifying potentially malicious domain lookups.

Outcome

DNS Proxy was successfully enabled, allowing Azure Firewall to manage DNS resolution for protected workloads. With routing, application filtering, network filtering, and DNS services fully configured, the Azure Firewall environment was ready for validation testing to confirm that security policies were functioning as expected.

Lessons Learned

This project reinforced the importance of centralized network security within cloud environments. Deploying Azure Firewall alone is not sufficient; traffic must be intentionally routed through the firewall using User Defined Routes to ensure inspection and policy enforcement.

This project reinforced my understanding that how multiple security controls work together to provide defense in depth. Application Rules, Network Rules, and DNS Proxy each address different aspects of network security, creating a layered approach that aligns with Microsoft's Zero Trust architecture principles.

Finally, validation testing highlighted the importance of confirming that security controls operate as intended. Successful deployment is only one part of the process—continuous verification ensures that security policies effectively protect cloud workloads.
